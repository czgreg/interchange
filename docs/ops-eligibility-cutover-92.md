## 已浮现的优化项(按观察驱动的优先级)

### O1 — 热重载瞬态:未探测节点被短暂纳入 → 池充胀 + 滞后剔除窗口
- **现象**:①9→18→12(切换后重启);②12→17(我为接 webhook 重启 leap-gateway 后,13 个在池节点 `probe_count=0`)。每次 **mihomo 热重载都会清空 url-test 历史** → 活节点暂判 `Qualified`(benefit-of-doubt)→ 进池;历史重建后真死节点才掉出。
- **根因**:eligibility 门对"无探针历史"的活节点给合格。**触发面比原判宽**:不只冷启,**任何热重载/重启都触发**(订阅增节点、运维重启)。
- **真实风险**:一个刚变坏的**在池**节点,在历史重建前(~一两轮)仍带流量。硬死有 mihomo 30s alive 位兜底;慢速变坏要等 url-test 重建。
- **已验证的缓解(现状已工作)**:新节点被 trial 挡住不进池(观察2 的 4 个 AWS2);已在池节点靠 poolSet 恢复(T0)留住不被误踢。所以瞬态影响面 = "已在池且历史被清"的节点,不是全体。
- **拟优化**:eligibility 要求 `ProbeCount >= min_probes` 才**新纳入**(已在池的沿用 poolSet 不受影响,避免热重载把老节点踢了)。
- **优先级**:**中**(已从"低"上调——触发面是每次热重载,不是罕见冷启)。但影响被 trial+poolSet 大幅限制,非紧急。
- **状态**:提案,未实现。**继续观察**:每次热重载后是否稳定重收敛、有无坏节点在窗口期带流量造成用户可感影响。

## 用户视角优化(实测 2026-08-31 ~12:xxZ,14 代理终端)

**关键重定义**:用户不关心池大小,关心"我这条出口稳不稳、快不快、失败率"。
实测:池大小 9→18→12→17 看着剧烈,但 **13/14 终端稳定钉在单一出口**,
HRW 黏性让池波动对个体用户基本不可见。**所以"波动太剧烈"从用户座位看
不成立**——churn 不是用户的痛点。真正的痛点是下面两个。

### U1 — 被 hash 钉在慢节点的用户,整段会话稳定慢(最大杠杆)
- **现象**:HRW 按 IP hash 分配、对质量盲目。池内既有 185ms(ash·GCP)
  又有 1242ms(Hutao BGP_D),被分到慢节点的 ~1/N 用户整段会话慢 5×,
  且 HRW 黏性让他一直待着。
- **用户感受**:比 churn 痛得多——churn 感觉不到,"一直卡"天天感觉到。
- **根因**:eligibility 只保证"活着"不保证"快";HRW 只均衡负载不均衡质量。
- **优化选项**(都需要一个"够用的"质量信号,不必是完整 per-destination):
  1. **质量加权 HRW / 粗分层**:gstatic p95 粗分 fast/slow 两层(带迟滞),
     慢层节点分到更少或零终端。改的是 `perterminal.go` 的 HRW 权重,不
     改 eligibility。风险:权重随质量变→引入一些重映射,要用迟滞+粗分层
     压制(只在跨越 fast/slow 边界时才调,不随噪声动)。
  2. **per-destination 真实信号**(§5/§8):最终解,但工程量大。
- **优先级**:**用户视角第一**。但需先确认:稳态下慢节点是否真的在带用户
  (当前 p95=0 重建中,待 url-test 恢复后复测 Hutao 慢节点的终端数)。
- **状态**:提案。**先测后动**——等信号重建,量化"多少用户被钉在 >600ms
  节点上、持续多久"。若占比小(如 <10% 且节点其实真实目的地可用),
  可能不值得引入加权 HRW 的复杂度+重映射代价。

### U2 — 单终端 fallback 翻动(尖锐但窄)
- **现象**:`10.8.12.144` 在 Hutao BGP_C↔BGP_E 间跳(fallback alive 位翻动,
  非池成员变化)。该用户出口 IP 中途变 = per_terminal 要防的反检测风险。
- **优先级**:中(仅 1 终端,但对他是真的)。
- **优化**:给 fallback 的 primary alive 位加去抖(短暂 alive=false 抖动不
  立即切 secondary),或让 secondary 选一个和 primary 不同订阅的 IP。
- **状态**:观察——是否持续跳、是否更多终端出现同现象。

### 用户视角的"波动"结论(回答"节点波动会不会太剧烈")
- **池大小波动**:监控里看着大(9↔18),但**对用户基本不可见**(HRW 黏性)。
- **单终端出口波动**:实测 13/14 稳定,1 条在跳(U2)。**当前不剧烈。**
- **真正影响体验的不是波动,是"被钉在慢节点"(U1)**——这是稳态问题,
  减少波动帮不到它。
